# Assumptions and Decisions

This file lists the points the brief left open and how I decided them.

## Platform

- **.NET 10 instead of .NET 8.** The brief asks for .NET 8 or newer. .NET 8 reaches end of support on 10 November 2026, so I used .NET 10, the current LTS release.
- **IDs are GUIDs.** Class and hold IDs are generated by the API. They can't be guessed, and they don't reveal how many records exist.
- **All timestamps are UTC** and returned in ISO-8601 format, e.g. `2026-11-09T08:09:37.453659+00:00`. They are stored with microsecond precision, the same as PostgreSQL.

## Running locally

- **Default database credentials live in `docker-compose.yml`.** They use the form `${POSTGRES_PASSWORD:-admission}`, so `docker compose up` works on a fresh clone without creating a `.env` file. To use real credentials, copy `.env.example` to `.env` and change the values. The defaults are only for local development.
- **PostgreSQL is exposed on host port 5433, not 5432,** so it doesn't clash with a PostgreSQL instance already running on the machine. Change it with `DB_PORT`. Inside the compose network the API still connects to `db:5432`.
- **The database schema is created automatically.** EF Core migrations run when the API starts, so no manual setup step is needed.
- **The API container runs as a non-root user** (the `app` user that ships with the .NET images) and listens on port 8080. Change the host port with `API_PORT`.
- **GSS (Kerberos) encryption is turned off in the connection string.** The API logs in to PostgreSQL with a password. Without this setting, Npgsql tries to load a Kerberos library that the slim runtime image doesn't include and writes a harmless but confusing error to the log.

## Students

- **There is no login.** The student is identified only by the `X-Student-Id` header, as the brief describes. The API trusts the header value.
- **A student ID is exactly 17 ASCII digits** (birth registration number). Leading and trailing spaces are trimmed. Anything else returns `400 INVALID_STUDENT_ID`.
- **`GET /holds/{id}` does not require the header,** because the contract doesn't list one for it. Anyone who knows a hold ID can read its status. Changing a hold (confirm or cancel) does require the owner's header; anyone else gets `403`.

## Classes

- **The class name is required.** It is trimmed and must be 1–200 characters. Names don't have to be unique, e.g. two schools may both have "Class 6".
- **`totalSeats` must be a whole number of at least 1.**
- **Classes can't be edited or deleted,** because the contract has no endpoints for it.
- **The API is documented with OpenAPI and stays on in every environment.** The interactive page is at `/swagger` and the raw spec at `/openapi/v1.json`, so reviewers can try every endpoint without the frontend. These two paths are additions; none of the contract endpoints change.
- **`POST /classes` returns the full class,** including `heldSeats`, `confirmedSeats` and `availableSeats`. The brief allows extra fields.

## Holds (applications)

- **One active application per student per class.** "Active" means `HELD` or `CONFIRMED`. After a hold expires or is cancelled, the student may apply again; this creates a new hold with a new ID.
- **A hold expires at `expiresAt`.** From that moment it can no longer be confirmed and its seat is released.
- **Confirming:**
  - A `CONFIRMED` hold returns `200` again without changing anything (idempotent).
  - An `EXPIRED` hold returns `409 HOLD_EXPIRED`.
  - A `CANCELLED` hold returns `409 HOLD_CANCELLED`.
- **Cancelling:**
  - A `HELD` hold becomes `CANCELLED` and its seat is released.
  - Cancelling a hold that is already `CANCELLED` or `EXPIRED` returns `204` (idempotent, as `DELETE` should be).
  - A `CONFIRMED` hold can't be cancelled (`409 ALREADY_CONFIRMED`), because the fee has been paid. Refunds are out of scope.
- **`GET /me/holds` returns all of the student's holds, newest first,** including expired and cancelled ones. This lets the student see the full history.

## Concurrency

- **Every seat change runs in a transaction that first locks the class row** with `SELECT ... FOR UPDATE`. PostgreSQL then handles requests for the same class one at a time, even when several API processes share the database. Requests for different classes still run in parallel.
- **The class row is always locked before its holds,** so two requests can't deadlock each other.
- **The database has two safety nets as well:**
  - a check constraint `held_seats + confirmed_seats <= total_seats`;
  - a partial unique index that allows only one active hold per student per class.
- **Each API process uses at most 20 database connections** (`Maximum Pool Size=20` in the connection string). PostgreSQL accepts 100 connections by default. Without this limit, two API processes under heavy load could use them all up. Extra requests wait for a free connection instead of failing.
- **Several API processes can share one database.** `docker compose --profile two-apis up` starts a second API on port 8081. When both start on an empty database, EF Core's migration lock lets only one of them apply the migration; the other waits. This was tested with a fresh volume.
- **If the database is overloaded anyway, the API returns `503 SERVICE_BUSY`** instead of `500`. The request was valid and can be retried.

## Expiry

- **A background service releases expired seats every 2 seconds,** even when nobody calls the API. The interval can be changed with `EXPIRY_SWEEP_INTERVAL_SECONDS`.
- **Every read or write of a hold also checks its expiry first,** so a request never sees an expired hold as `HELD`, even between two sweeps.
- **Seat counts in `GET /classes` may still include an expired hold for up to one sweep interval.** This only delays when the seat shows as free again. It can't cause overbooking, because creating a hold expires that class's overdue holds first.
- **The sweeper is safe to run in several API processes at once.** It expires holds under the same class row lock as everything else, so a seat is never released twice.

## Frontend

- **React 19 instead of 18.** The brief asks for React 18 or newer, and the current Vite template uses React 19. The app uses TypeScript.
- **The UI is in Bengali.** Each status badge also shows the raw status code (e.g. `মেয়াদ শেষ EXPIRED`), so the four contract statuses are visible as named.
- **The student ID is remembered in `localStorage`.** On a refresh, or after closing and reopening the browser, the ID comes back. "My applications" then reloads the student's applications from `GET /me/holds`. Nothing else is stored in the browser; the server is the only source of truth.
- **Refresh interval: 3 seconds.** This applies to the class list (seat counts), the application screen and "My applications". A new request starts only after the previous one finished.
- **Expiry on screen.** The countdown uses the browser's clock. When it reaches zero, the screen shows `EXPIRED` and disables the pay button immediately, without waiting for the server. If the browser's clock is off, the server's decision still wins: a late payment is refused with `409` and the screen updates.
- **The API address is set when the container starts, not when the image is built.** The frontend container writes `config.js` from the `API_URL` environment variable (default `http://localhost:8080`), so the same image works with any backend address. The browser calls the API directly, so `API_URL` must be reachable from the user's machine, not only from inside Docker. For `npm run dev`, use `VITE_API_URL`.
- **Anyone can create a class.** The brief has no admin role, so the "create class" screen is open to everyone.
- **The application screen is reached by its hold ID** (`/holds/<id>`). The pay and cancel buttons send the student ID from the top box. If it belongs to someone else, the server refuses with `403`, and the screen explains this.
- **The frontend is served by nginx on host port 3000** (change with `FRONTEND_PORT`). Unknown paths fall back to `index.html`, so deep links and refreshes work.

## Errors

- **Every error response has the same shape:** `{ "error": "NO_SEATS_AVAILABLE", "message": "..." }`. `error` is a stable code the frontend can check. `message` is readable text.
- **Bad input returns `4xx`, never `500`.** This covers invalid JSON, wrong field types, a wrong content type and malformed IDs in the URL. A route ID that isn't a valid GUID returns `404`.
